## 프로젝트 소개

TravelPay 는 원화 충전, 회원 간 송금, 외화 환전, 가맹점 결제를 하나의 지갑에서 제공하는 여행자용 금융 플랫폼입니다. 모든 자금 이동을 공용 원장에 복식부기(차변 · 대변)로 한 번만 기록하고, 결과를 모르는 거래는 다시 처리해 확정하는 것이 시스템 전체의 원칙입니다.

5인 팀 프로젝트에서 **송금 백엔드와 프론트엔드 전체**를 담당했습니다.

백엔드에서는 송금 요청부터 원장 반영, 결과 불명 상태 복구, 자동 대사까지 이어지는 거래 흐름을 설계했습니다. 프론트엔드에서는 금전 요청의 멱등성 키와 결과 불명 상태를 일관되게 처리해 사용자의 중복 거래를 방지했습니다.

단순한 기능 구현보다 여러 요청이 동시에 들어오거나 외부 시스템의 응답이 유실되는 상황에서도 **잔액과 거래 기록이 일치**하도록 만드는 데 집중했습니다.

- 기간: 2026.10 — 2026.11 · 5인 팀. 백엔드는 팀 저장소 [dont-worrys/travelpay](https://github.com/dont-worrys/travelpay) 에서 개발한 뒤 개인 포크에서 이어 개발했습니다.
- 서비스: Eureka · Gateway · user · wallet · payment · exchange · ledger(공용 원장) · mock-bank(외부 은행 대체), 8개 MSA 서비스. 송금은 결제와 같은 payment-service 안에 있습니다.
- 기술: Java 21, Spring Boot 4, Spring Data JPA, PostgreSQL, Spring Cloud Gateway, Eureka, OpenFeign, Resilience4j, React 19, TypeScript, React Router 7, Vite 7, Vitest, Testcontainers, k6, Prometheus, Grafana

송금 요청(`POST /api/v1/transfers`)은 다음 순서로 처리합니다.

1. Gateway 가 세션 · CSRF 를 확인하고, 클라이언트가 보낸 회원 헤더를 지운 뒤 검증한 값으로 다시 넣어 payment-service 로 넘깁니다.
2. 같은 송금인 · 같은 `Idempotency-Key` 의 송금이 이미 있으면 원장을 부르지 않고 멱등성 규칙으로 응답합니다.
3. 송금인 지갑, 수취인 회원, 수취인 지갑이 사용 가능한지 확인합니다. 빠른 거절용이며, 여기서 실패하면 송금을 저장하지 않아 같은 키로 다시 요청할 수 있습니다.
4. 송금을 `PROCESSING` 으로 저장 · 커밋한 뒤, DB 트랜잭션 밖에서 원장에 거래 하나(reference `TRANSFER + 송금 ID`)를 등록합니다.
5. 원장 결과에 따라 201 `COMPLETED`, 422 `FAILED`(잔액 부족 · 계정 사용 불가), 202 `PROCESSING`(결과 모름), 202 `MANUAL_REVIEW`(원장 409 · 400)로 응답합니다.

## 핵심 구현 및 설계 결정

### 1. 원장 위임형 송금과 데이터 정합성

**배경** — 서비스마다 DB 가 따로 있고 잔액은 원장 서비스가 가집니다. 송금인 차감과 수취인 입금 중 한쪽만 반영되면 안 됩니다.

**설계 · 구현**

- 송금 서비스에서 송금인 잔액을 차감하고 수취인 잔액을 별도로 증가시키는 대신, 원장에 하나의 거래로 등록하도록 설계했습니다. 송금인 지갑 DEBIT `TRANSFER_OUT` 과 수취인 지갑 CREDIT `TRANSFER_IN` 두 줄을 함께 보냅니다.
- 원장이 한 DB 트랜잭션에서 차변 · 대변을 함께 처리하므로 한쪽만 반영되는 문제를 방지합니다. 송금은 잔액을 직접 바꾸지 않고 상태만 관리합니다.
- 원장 호출 전에 송금을 `PROCESSING` 으로 먼저 커밋하고, 호출은 트랜잭션 밖에서 합니다. 어느 시점에 서버가 멈춰도 송금 행이 먼저 남아 복구 대상이 되고, 원장을 기다리는 동안 DB 커넥션을 잡지 않습니다.
- 검토한 대안: 차감 · 입금 API 를 따로 부르고 실패 시 보상(Saga)하는 방식은 차감만 된 구간과 보상 실패 처리가 생기고, 잔액을 먼저 조회한 뒤 차감하는 방식은 조회와 차감 사이 경합을 막지 못해 택하지 않았습니다.
- **감수한 점**: 요청당 커밋이 2번이고, 한 계정에 거래가 몰리면 원장 행 잠금으로 처리가 직렬화됩니다(아래 트러블슈팅).

**검증** — 부하 측정 뒤 송금 · 원장 · 잔액 전수 대사에서 위반 0건. 수취인 집중 측정에서 원장 처리 시간이 평균 166ms 로 늘어도 payment 커넥션 사용은 평균 1.1개, 대기 0이었습니다.

### 2. 송금 멱등성

**배경** — 금전 POST 는 같은 키 · 같은 내용이면 같은 결과, 같은 키 · 다른 내용이면 409 여야 하고, 동시에 들어온 중복도 막아야 합니다.

**설계 · 구현**

- `Idempotency-Key` 를 송금 행에 저장하고 DB `UNIQUE(sender_id, idempotency_key)` 로 중복을 막습니다. 키와 송금이 한 행이라 "키만 저장된" 상태가 없습니다.
- 여기에 더해, 저장된 요청 값(수취인 · 금액 · 통화 · 정규화한 메모)과 비교해 같은 키로 다른 요청이 들어오는 경우를 409 `TRANSFER_IDEMPOTENCY_KEY_REUSED` 로 걸러 냈습니다.
- 처음에는 네 값의 SHA-256 을 `request_hash` 컬럼에 따로 저장했지만, 같은 정보를 두 번 저장하는 셈이라 컬럼을 지우고 저장된 값을 직접 비교하도록 바꿨습니다(#304).
- 같은 키 재요청은 원장 · 지갑 · 회원을 다시 부르지 않고 현재 상태로 응답합니다. Redis 키 저장은 만료 · 장애 때 중복 송금 경로가 생겨 쓰지 않았습니다.

**검증** — 같은 키 · 같은 본문 20건 동시 요청에서 송금 1건 · 원장 호출 1번(`TransferConsistencyIntegrationTest`). 실제 원장으로 20라운드 × 동시 20건(400건)을 보내 송금 20건, 다른 본문 100건은 모두 409 였습니다.

### 3. 결과 불명 상태와 자동 복구

**배경** — 외부 원장 호출에서 타임아웃이 발생해도 실제 거래가 반영됐을 가능성이 있습니다. 실패로 응답하면 사용자가 새 키로 다시 보내 이중 송금이 될 수 있습니다.

**설계 · 구현**

- 따라서 실패로 확정하지 않고 `PROCESSING` 상태로 보존한 뒤(202), 복구 스케줄러가 동일 reference 로 재전송합니다. 원장은 같은 reference 를 한 번만 처리하므로 재전송해도 잔액은 한 번만 바뀝니다.
- 원장을 먼저 조회하지 않고 같은 reference 로 바로 다시 보냅니다. 같은 reference 에 내용이 다른 거래가 있으면 재전송은 409 로 드러나지만, 조회만 하면 잘못 `COMPLETED` 로 확정할 수 있기 때문입니다.
- 재시도 간격은 30초 × 2^(n−1)(30초 · 1분 · 2분 · 4분)이고, 한 주기에서 결과 모름이 연달아 3번이면 원장 장애로 보고 남은 건을 미룹니다. 결과 불명 거래는 재시도 5회를 넘으면 `MANUAL_REVIEW` 로 넘깁니다.
- 재시도가 소진된 거래는 `MANUAL_REVIEW` 로 격리하고 원장 기록을 직접 대조해 자동 확정하도록 구현했습니다(#301). 약 1분마다 원장 reference 를 조회해 `POSTED` 이고 항목이 송금과 같으면 `COMPLETED`, `REJECTED` 면 `FAILED` 로 확정합니다. 기록이 없거나 항목이 다르면 확정하지 않고 운영자에게 남깁니다.
- 운영자 확정 API 도 운영자 입력을 믿지 않고 서버가 원장 항목(지갑 · 방향 · 통화 · 금액 · 유형)을 직접 대조하며, 상태를 바꾸지 않는 미리보기 API 를 따로 두었습니다.
- 30분 넘게 `PROCESSING` 인 송금 수와 `MANUAL_REVIEW` 대기 수를 지표로 노출하고, 로컬 Grafana 알림 규칙으로 발동 · 해소까지 확인했습니다.

**검증** — 실제 원장으로 응답 유실 → 원장 정지로 재시도 소진 → `MANUAL_REVIEW`(생성부터 7분 39초) → 원장 정지 중 자동 대사 조회 실패로 유지 → 원장 복구 뒤 자동 대사가 `COMPLETED` 로 확정하는 흐름을 확인했습니다. 재전송이 4번 있었지만 원장 거래는 1건, 잔액은 1회만 바뀌었습니다. 부하 중 응답 유실(원장 읽기 타임아웃 25ms 주입)에서도 202 응답 184건을 130초 안에 모두 복구했습니다(최대 시도 2회, `MANUAL_REVIEW` 0, 송금 2,664건 = 원장 거래 2,664건).

### 4. 분산 락 없는 동시성 제어

**배경** — 요청 · 복구 스케줄러 · 자동 대사 · 운영자가 같은 송금 행을 동시에 바꿀 수 있고, 서버가 여러 대면 복구 대상도 겹칩니다.

**설계 · 구현**

- 경합 지점을 UNIQUE, 조건부 UPDATE, SKIP LOCKED, 원장 reference 멱등성으로 방어했습니다. 중복 요청은 DB UNIQUE, 상태 변경은 조건부 UPDATE, 다중 서버의 복구 대상 선점은 `FOR UPDATE SKIP LOCKED` 로 처리했습니다.
- 모든 상태 변경은 시작 상태를 조건으로 건 UPDATE 이고, 0행이면 다른 경로가 먼저 바꾼 것으로 보고 다시 읽은 상태를 따릅니다. 허용 전이가 WHERE 조건에 그대로 드러납니다.
- 이전 복구 방식은 모든 서버가 같은 앞쪽 10건을 두고 경쟁해 서버가 늘어도 주기당 합계 10건이었습니다. 대상 조회와 선점을 SKIP LOCKED 한 문장으로 합쳐, 다른 서버가 잠근 행은 건너뛰고 서버마다 10건을 가져가도록 바꿨습니다(#310).
- 한 번에 선점한 10건을 차례로 보내는 동안 선점이 만료될 수 있어, 원장 호출 직전에 "이번 선점 시각 그대로일 때만" 갱신하는 조건부 UPDATE 로 다시 확인합니다.
- 분산 락에 의존하지 않고 데이터베이스의 원자적 연산과 원장 멱등성을 최종 방어선으로 사용했습니다. ShedLock 은 한 서버만 돌아 처리량이 늘지 않고 잠금 만료 때 여전히 겹칠 수 있어 택하지 않았습니다.

**검증** — 조건부 UPDATE 10가지 × 시작 상태 6개 전이표(`TransferStatusTransitionIntegrationTest`), 서버 2대 동시 복구 테스트에서 주기당 10건 → 20건 · 송금마다 재전송 1번, 자동 대사 2대 동시 실행 시 확정 · 이력 1건, 운영자 동시 확정 8건 중 1건 성공 · 이력 1건. 서버 2대 테스트는 같은 DB 에 스레드 2개로 동시 실행한 것이며, 실제 서버 2대 기동 확인은 하지 않았습니다.

### 5. 프론트엔드 금전 요청 안정성

**배경** — 프론트엔드에서도 금전 요청의 결과를 임의로 실패 처리하면, 사용자가 다시 보낸 요청이 새 거래가 됩니다.

**설계 · 구현**

- 충전 · 송금 · 결제 · 환불 · 정산 · 환전 · 예약 환전 등 금전 POST 7종에 `Idempotency-Key` 를 적용했습니다. 사용자 동작 한 번에 UUID 키 하나를 만듭니다.
- 연결 실패 · 5xx · 타임아웃을 실패로 단정하지 않고 결과 확인 필요 상태로 안내하며, "다시 시도"는 같은 키로 보냅니다. 서버가 판단을 끝낸 응답(2xx · 4xx)을 받으면 다음 요청은 새 키를 씁니다.
- 같은 키를 다시 쓰는 조건은 화면마다 서버가 비교하는 값과 맞췄습니다. 예를 들어 송금 · 충전은 본문 전체, 환전은 같은 견적일 때입니다.
- 결과 불명 상태에서는 입력값이나 견적을 변경해 새로운 요청을 만들지 못하게 하고, 기존 멱등성 키로만 재시도하도록 구성했습니다.
- 금전 POST 에는 클라이언트 대기 한도를 두지 않았습니다. 끊으면 서버가 처리했는지 알 수 없기 때문이며, GET 만 15초에 끊습니다.
- 그 밖에 React.lazy 기반 라우트 코드 스플리팅과 vendor 청크 분리로 앱 시작 청크를 560kB 에서 33.9kB 로 줄였고, 환율 티커와 환전 화면이 같은 환율 조회를 공유하도록 바꿔 환율 화면 진입 시 API 요청을 2회에서 1회로 줄였습니다.

**검증** — 금전 요청 화면 테스트에서 보내는 본문 · 헤더, 결과 모름 시 같은 키 재전송, 내용 변경이나 4xx 뒤 새 키를 확인했습니다. Gateway 경유 E2E 로 송금 109건 · 예약 환전 86건을 보내 모두 예상대로 응답했고, 서비스 로그 ERROR 는 0건이었습니다.

### 6. 개인 확장 — 송금 완료 알림

팀 프로젝트 종료 후 개인 포크에서 송금 완료 알림 기능을 추가했습니다.

- 송금 완료와 Outbox 이벤트 저장을 같은 트랜잭션으로 처리하고, Kafka 발행 · 소비 및 DLT 를 통해 알림 전달을 분리했습니다.
- user-service 가 eventId 로 중복을 걸러 보낸 · 받는 사람 화면 알림과 Slack 알림을 남깁니다. Slack 실패가 재시도 뒤에도 이어지면 DLT 로 보내고 다음 메시지를 처리합니다.
- Kafka 가 중단되어도 송금은 완료되며, 복구 후 이벤트를 발행하도록 구성했습니다. 이벤트는 같은 eventId 로 다시 발행되므로 소비자에서 한 번만 처리됩니다.
- 원장 연동 자체는 동기 HTTP 로 두었습니다. 원장 결과가 사용자 응답(201 · 422 · 202)에 바로 필요하기 때문입니다.

※ Outbox · Kafka · DLT 알림은 팀 프로젝트의 기본 구현이 아닌 개인 포크에서 추가한 확장 작업입니다.

## 성능 개선 및 검증

**목적** — 수취인 집중 시 처리량이 떨어지는 원인을 찾고, 개선을 적용해 같은 조건에서 전후를 비교했습니다.

**원인 분석** (2026-11-11)

- 기준 측정(동시 20, 60초)에서 분산 송금 161.3 TPS, 수취인 집중 93.5 TPS 로 약 42% 낮았고, 원장 커넥션 10개 중 평균 8.3개가 잠금 대기였습니다. 원장 커넥션 풀을 늘려도 대기만 늘어 효과가 없었습니다.
- 0.05초마다 잠금을 쥔 원장 세션의 상태를 표본으로 모아 보유 시간을 나눴습니다. 앱이 다음 SQL 을 보내길 기다림 70.8%, 앱에서 메시지를 받는 중 11.9% 로 합계 82.7% 가 왕복 대기였고, DB 가 실제로 일한 시간(문장 실행 · COMMIT)은 건당 약 1.8ms 였습니다.
- 원장은 잠근 뒤 거래 INSERT, 항목 INSERT 2번, 계정 UPDATE 2번, COMMIT 을 따로 보내고 있었습니다. Hibernate `jdbc.batch_size` · `order_inserts` · `order_updates` 를 켜 잠금 뒤 왕복을 6번에서 4번으로 줄였습니다(원장 코드 변경 없음, 원장 테스트 111건 통과).

**측정 조건** (2026-11-12)

- 원장만 Docker 컨테이너(같은 네트워크의 Postgres 에 직접 연결), 다른 서비스는 노트북에서 `java -jar`, 모니터링 켬, payment 직접 호출
- k6, 수취인 집중 모드, 동시 20 · 60초, 회차마다 예열 30초(버림), 전후 각 2회
- before · after 모두 새로 준비한 같은 데이터, 설정만 바꿔 원장 컨테이너를 다시 띄워 전환

**결과** (2회 평균)

| 지표 | before (batch 끔) | after (batch 켬) | 변화 |
| --- | --- | --- | --- |
| 성공 TPS | 151.3 | 170.4 | **+13%** |
| 건당 잠금 보유 | 6.69ms | 5.93ms | −11% |
| 원장 POST 평균 | 81ms | 66ms | **−18%** |
| 202 · 오류 · 대사 위반 | 0 | 0 | |

**해석**

- 효과는 있지만 작은 편입니다. before 두 회차 차이가 약 10% 라 회차를 늘리면 더 분명해집니다.
- 원장도 노트북에서 띄운 환경(DB 포트 전달)에서는 TPS +25% 로 개선 폭이 더 컸지만 꼬리 지연이 크게 나빠졌습니다. 앱 ↔ DB 왕복이 비싼 환경이라 왕복을 줄인 효과도, 잠금 경쟁도 커진 것으로 보며, 이 원인을 따로 검증하지는 않았습니다. 82.7% 도 이 측정 환경에서의 비율입니다.
- 급증(초당 20 → 300건) 동안 처리 한계 근처인 158.1 TPS 까지 202 · 오류 없이 대기 지연으로 흡수하고, 급증이 끝나자 바로 이전 지연으로 돌아왔습니다(대사 8,422건 위반 0).

**그 밖의 검증 · 개선**

- 30분 부하 테스트 약 32만 건(318,334건, 176.9 TPS), 송금 · 원장 대사 위반 0. GC 뒤 남는 메모리 · 스레드 · 커넥션이 30분 내내 평탄해 누수 신호가 없었습니다.
- 양방향 동시 송금 20,515건에서 교착 0, 잔액 합계 보존.
- 요청 지연 분석으로 지갑 · 회원 Feign 읽기 타임아웃을 3초 → 1초로 줄였습니다(지갑 · 결제 · 회원 담당 동의). 측정 최대 응답(112ms 이하)의 약 9배이며, 원장 읽기 타임아웃 축소는 정상 거래를 미확정으로 만들 수 있어 결제 담당 의견대로 보류했습니다.
- `MANUAL_REVIEW` 건수 · 자동 대사 대상 조회가 테이블 전체를 읽고 있어 부분 인덱스를 추가했습니다. 로컬 102만 행 기준 건수 조회 52ms → 0.04ms 였습니다.

**한계** — 성능 수치는 노트북 단일 환경의 로컬 측정으로, 절대 성능보다는 병목 분석과 전후 비교에 의미가 있습니다. 서비스와 DB 사이 포트 전달, CPU 포화가 섞여 있고 측정마다 1~2회라 목표 수치(SLO) 판정은 하지 않았습니다.

## 한계 및 개선 방향

- 수취인 집중 병목의 근본 해결인 계정 분할은 원장 공통 과제로 남았습니다.
- 다중 서버 복구는 같은 DB 에 스레드 2개를 띄운 테스트로만 확인했습니다.
- 개인 포크의 알림 기능은 로컬 검증 단계이며 운영 환경에서는 발행기와 소비자가 비활성화되어 있습니다.
