## 프로젝트 소개

Windows 디스크에서 무엇이 공간을 차지하는지 빠르게 찾고, `node_modules` · npm · pip · Gradle 캐시 같은 **개발 환경 찌꺼기를 안전하게 정리**하는 도구입니다.
개발을 하다 보면 프로젝트마다 쌓이는 의존성 · 빌드 결과물과 도구별 공용 캐시가 디스크를 크게 차지하지만, 무엇을 지워도 되는지 판단하기 어렵습니다. 그래서 "어디가 큰지"뿐 아니라 "지우면 실제로 얼마가 비는지, 지워도 다시 만들 수 있는지"까지 보여 주고, 지울 때는 되돌릴 수 있는 방식만 쓰는 것을 목표로 했습니다.

- 기간: 2026.10 — 2026.11 · 개인 프로젝트
- 형태: 명령줄 도구(`disk-scanner`)와 GUI(`bytesieve-gui`)가 같은 Core 를 공유하는 Windows 데스크톱 앱
- 기술: 외부 라이브러리 없이 **C11 과 Win32 API 만으로** 작성, CMake 3.21+ · MSVC, Inno Setup 6, GitHub Actions
- 지원 환경: Windows 10 / 11 x64. Core 가 Win32 API 에 묶여 있어 macOS · Linux 는 지원하지 않습니다.
- 배포: 최신 릴리스는 [v1.0.1](https://github.com/gajigaji-dev/ByteSieve/releases/tag/v1.0.1)(2026-11-14)이며, 설치 프로그램 · 포터블 zip · SHA-256 체크섬 파일을 함께 배포합니다.

### 주요 기능

- **폴더 스캔과 트리맵** — 폴더별 용량을 트리 · 목록 · squarified 트리맵으로 표시하고, 직전 스캔 기록과 비교해 늘어난 폴더를 보여 줍니다.
- **실제 확보 용량 계산** — 할당 크기 · 하드 링크 수 · 압축 크기를 반영해 "지우면 실제로 비는 용량"을 계산하고, 클라우드 파일은 내려받지 않고 읽습니다.
- **안전한 정리** — 영구 삭제 대신 휴지통 이동(실행 취소 가능) 또는 격리 폴더 이동 · 복원을 지원합니다. CLI 의 `clean` 은 기본값이 `--dry-run` 입니다.
- **Git 프로젝트 분석** — 프로젝트별 미커밋 변경 · 푸시하지 않은 커밋을 읽기 전용으로 확인해 정리 판단을 돕습니다.
- **시스템 정리 · 개발 캐시** — 임시 파일 · 오류 보고서 · 브라우저 캐시와 공용 개발 캐시(npm · pip · Gradle · Cargo · NuGet 등)를 분석합니다.
- **그 밖의 도구** — 드라이브 · BitLocker 상태, CPU · RAM 모니터, CSV · HTML 내보내기, WSL · Docker 가상 디스크 탐지

## 핵심 구현 및 설계 결정

### 1. 병렬 미리 열거 스캐너

**배경** — 한 스레드로 폴더를 깊이 우선 열거하면 `C:\Windows`(파일 21만 · 폴더 16만) 스캔에 16초 넘게 걸렸습니다.

**설계 · 구현**

- 호출 스레드는 깊이 우선 순서를 그대로 지키고, 작업 스레드 풀(기본 논리 프로세서 수, 최대 8개)이 곧 필요할 하위 폴더를 **미리 열거**해 둡니다. 훅은 언제나 호출 스레드에서 병렬이 아닐 때와 같은 순서로 불리므로, 결과 · 오류 순서가 스레드 수와 관계없이 같습니다.
- 스레드 풀은 `SRWLOCK` 과 조건 변수로 동기화하고, 최소 힙 큐에 상한을 두어 한도가 차면 가장 늦게 필요한 작업을 내보냅니다. 최대 사용량은 `InterlockedAdd64` · CAS 로 집계합니다.
- 폴더 열거는 `GetFileInformationByHandleEx` 로 합니다. 하드 링크 중복을 보정하는 정밀 스캔에서는 파일 ID 가 필요해 `FileIdExtdDirectoryInfo`(128비트 ID)를 우선 쓰고, 지원하지 않는 볼륨에서는 `FileIdBothDirectoryInfo`(64비트 ID)로 내려갑니다.

**검증** — `scan_parallel` 테스트에서 작업 스레드 1개와 8개의 집계 · 훅 호출(순서 포함)이 같은지, 직접 열거 + 미리 열거 − 버림 = 처리한 폴더 수(빠뜨리거나 두 번 세지 않음)인지 확인합니다. 시간 · 메모리 수치는 아래 [성능 측정](#성능-측정)에 정리했습니다.

### 2. 안전한 정리 — 되돌릴 수 있는 방식만

**배경** — 정리 도구는 한 번의 잘못된 삭제가 치명적이라, 무엇을 지울 수 있는지보다 "무엇을 절대 건드리지 않을지"를 먼저 정했습니다.

**설계 · 구현**

- 정리 경로에는 영구 삭제 코드가 없습니다. 휴지통 이동은 Shell `IFileOperation` 에 `FOFX_RECYCLEONDELETE | FOF_ALLOWUNDO` 를 지정해 항목마다 되돌릴 수 있게 옮깁니다.
- 셸이 영구 삭제로 바꾸려 하면(휴지통 용량 초과 등) 거부하고, 휴지통이 없는 이동식 드라이브는 처음부터 **같은 볼륨의 격리 폴더**(`X:\.bytesieve-trash\`)로 옮깁니다. 기록을 먼저 쓰고 `MoveFileExW` 로 이름만 바꾼 뒤 기록을 고치며, 격리한 항목은 복원하거나 두 번 확인한 뒤에만 영구 삭제합니다.
- 경로 판정에서 Windows · `Program Files` · 사용자 프로필 · 알려진 폴더 · 개발 도구와 프로그램 설치 경로, 하위를 다 읽지 못한 항목 등을 거부합니다.
- 옮기기 직전에 한 번 더 확인합니다. 탐지 때와 종류가 다르거나 링크로 바뀌었거나, `GetFinalPathNameByHandleW` 로 구한 실제 위치가 표시 경로와 다르면(중간 폴더가 정션으로 바뀐 경우 등) 건드리지 않습니다.
- GUI 의 세 정리 페이지와 CLI 는 같은 정리 계획(`clean_plan`)으로 고르고 실행하므로 보호 조건이 똑같이 적용됩니다. CLI 는 `--execute` 없이는 아무것도 옮기지 않고, 대화형이 아닌 입력에서는 `--yes` 없이 실행하지 않습니다.

**검증** — CLI 검사(`cli_clean_project` · `cli_clean_system`)에서 기본 · `--dry-run` 이 아무것도 옮기지 않는지, 비대화형 입력에서 `--yes` 없는 실행이 거부되는지 확인합니다. GUI 자체 검사(`gui_trash` · `gui_trash_fallback` · `gui_quarantine`)는 휴지통 이동, 격리 폴더로의 대체 경로, 복원(같은 이름은 건너뜀) 결과를 확인합니다.

### 3. 실제 확보 용량과 Git 프로젝트 분석

**배경** — 폴더 크기만으로는 "지우면 얼마가 비는지", "지워도 되는지"를 알 수 없습니다. 하드 링크로 다른 곳과 공유하는 파일이나 작업 중인 프로젝트가 있기 때문입니다.

**설계 · 구현**

- 정리 항목 안의 파일마다 할당 크기 · 하드 링크 수 · 파일 ID 를 조회합니다. Windows 11 24H2 이상은 `GetFileInformationByName` 으로 파일을 열지 않고, 그 전에는 속성 읽기 권한으로만 열어 조회하므로 파일 내용을 읽지 않고 클라우드 파일도 내려받지 않습니다.
- 압축 · 스파스 파일은 실제 점유량으로, 링크가 여러 개인 파일은 항목 안에서 모든 링크를 봤을 때만 확보 가능으로 셉니다.
- 후보를 가장 가까운 Git 저장소별로 묶어, 미커밋 변경이 있는 프로젝트는 [모두 선택] · CLI 기본 선택에서 빼고, 푸시하지 않은 커밋은 알리기만 합니다. 후보마다 lockfile 기준으로 다시 설치해 복구할 수 있는지도 보여 줍니다.
- Git 분석은 읽기 전용입니다. git.exe 를 `--no-optional-locks` · `-c core.fsmonitor=false` 로 창 없이 시간 제한을 두고 실행하고, git 이 없으면 `.git` 을 직접 읽습니다.

**검증** — `cli_find` 검사에서 프로젝트마다 Git 저장소를 만들어 휴면 판정 · 미커밋 변경 · 원격 없는 커밋 · lockfile 복구 가능성을 확인하고, 아무것도 옮기지 않는지도 확인합니다. `reclaim` 단위 테스트는 하드 링크 픽스처로 항목 밖과 링크를 나누는 파일이 공유로 빠지는지 확인합니다.

### 4. 순수 Win32 GUI 와 작업 스레드 분리

**설계 · 구현**

- 스캔은 별도 스레드에서 돌고, 진행률 스냅숏은 `CRITICAL_SECTION` 으로 보호하며 취소는 Interlocked 플래그로 처리합니다.
- comctl32 TreeView · ListView 와 GDI 로 그리고, DWM 속성과 `SetWindowTheme` 으로 다크 모드를, `WM_DPICHANGED` 로 고배율 모니터를 처리합니다.
- GUI 는 한국어 · 영어 · 일본어 · 중국어 간체 4개 언어를 지원합니다. 문구는 번역 표 하나에 모으고, Core 의 상태 문구는 그대로 둔 채 GUI 에서 번역 표로 연결했습니다.

**검증** — GUI 자체 검사는 숨긴 창에서 실제 작업을 실행하고 화면 상태를 확인합니다. DPI 배율 100 · 125 · 150 · 200% 마다 네 언어 × 다섯 창 크기로 바꿔 가며 모든 페이지의 컨트롤이 패널 안에 있고 겹치거나 잘리지 않는지 확인하고(`gui_layout_*`), 테마 전환 시 목록 · 트리의 배경 · 글자 색을 확인합니다(`gui_theme`).

## 성능 측정

`bytesieve-bench` 로 실행 시간 · 최대 메모리와 스캐너 내부 진단값을 측정했습니다. 디스크 캐시 차이를 줄이려고 개선 전후 실행 파일을 같은 시간대에 번갈아 돌렸습니다.

**조건** — Windows 11, 논리 프로세서 12개, `C:\Windows`(파일 21만 · 폴더 16만), 디스크 캐시가 찬 상태, Release 빌드

**병렬 미리 열거 도입**

| 모드 | 개선 전 | 개선 후(8 스레드) |
| --- | --- | --- |
| tree(집계만) | 16.4 s | **3.2 s** |
| model(GUI 트리 구성) | 16.4 s | **3.1 s** |
| cleanup(정리 후보 탐지) | 16.6 s | **3.3 s** |

**병렬 스캔 메모리 최적화**(tree 모드, 8 스레드)

| 항목 | 개선 전 | 개선 후 |
| --- | --- | --- |
| 동시 폴더 작업 수 | 52,000 | **1,040** |
| 프로세스 최대 메모리 | 58 MiB | **39–41 MiB** |
| 시간 | 3.1–3.4 s | 3.2–3.4 s |

**GUI 스캔 완료 처리**(`C:\Windows`, 직전 기록이 있는 상태)

| 항목 | 개선 전 | 개선 후 |
| --- | --- | --- |
| 직전 기록과 비교 | 150–195 ms | **50–56 ms** |
| UI 스레드 점유(평균) | 313 ms | **40 ms** |

- 로컬 단일 머신 측정이라 절대 수치가 아닌 같은 환경의 전후 비교로만 봅니다. 파일 · 폴더 수는 모든 실행에서 같았습니다.
- 측정용 타이머는 측정 후 제거했습니다. 측정 방법과 세부 수치는 저장소 `docs/performance.md` 에 남겼습니다.

## 테스트와 릴리스

- **테스트**: CTest 에 단위 테스트 31개, CLI · 도구 검사 32개, GUI 자체 검사 34개(총 97개)를 등록했습니다(v1.0.1 문서 기준). 배포하는 Release 구성으로 모두 통과해야 합니다.
- **CI**: `main` · `dev` push 와 PR 마다 GitHub Actions(`windows-latest`)에서 Release 빌드 후 `ctest -C Release` 를 실행합니다.
- **릴리스 자동화**: `v*` 태그를 올리면 패키징 → 설치 프로그램 테스트 → draft 릴리스까지 GitHub Actions 로 처리합니다. 릴리스 본문은 `CHANGELOG.md` 의 해당 버전 구역에서 만듭니다.
- **설치 프로그램**: Inno Setup 6 으로 관리자 권한 없이 사용자별로 설치합니다. 제거할 때 격리 폴더와 스캔 기록은 자동으로 지우지 않습니다.
- **설치 프로그램 자동 검증**: 테스트 전용 AppId 와 레지스트리 키로 실제 설치본과 겹치지 않게 새로 설치 · 업그레이드(언어 설정 유지) · 실행 중 업그레이드 차단 · 제거를 확인합니다.
- **v1.0.1 변경점**: GUI 4개 언어(한국어 · 영어 · 일본어 · 중국어 간체) 즉시 전환, Per-Monitor DPI V2, 직전 기록 비교 속도 개선(150–195ms → 50–56ms), 비교 · 저장 작업을 작업 스레드로 이동

알려진 제한(v1.0.1): 코드 서명 없음, 다크 모드에서 일부 대화상자가 밝게 표시됨, HTML 보고서와 CLI 는 한국어만 지원.
