## 프로젝트 소개

Spring Boot 기반의 배달 서비스로, 고객의 주문부터 결제, 사장님의 주문 처리, 일 정산과 환불까지 이어지는 서비스 흐름을 구현했습니다.

단순한 CRUD 구현을 넘어 금융 거래에서 발생할 수 있는 **중복 요청, 외부 결제사의 응답 지연, 이벤트 유실, 정산 금액 불일치** 등의 문제를 해결하는 데 집중했습니다. 돈이 오가는 흐름(주문 → 결제 → 정산 → 환불)에서 중복 · 유실 없이 기록을 맞추는 것이 설계 결정 대부분의 출발점이었습니다.

React 기반 고객 · 사장님 · 관리자 화면을 구현하고, 실제 배포 환경에서 체험할 수 있는 데모 기능까지 구성했습니다.

- 기간: 2026.10 — 2026.11 · 1인 개인 프로젝트
- 배경: 스파르타 단기 심화 온보딩 주차 과제(주문 · 결제)로 시작해 수수료, 일 정산, 환불 · 이월, 정산 감사 이력 · 재집계, 이벤트 발행, PG 연동, 화면과 배포까지 확장했습니다.
- 주요 흐름: 고객 주문 → 결제(토스페이먼츠 테스트 모드) → 사장님 수락 → 배달완료 → 일 정산 집계 → 관리자 확정 → 지급, 배달 후 환불은 다음 정산에서 차감 · 이월
- 역할 3단계: 고객(CUSTOMER) · 사장님(OWNER) · 관리자(ADMIN)
- 기술: Java 21, Spring Boot 4.1, Spring Security · JWT, Spring Data JPA, PostgreSQL 18 · Flyway, Redis 8, Kafka 4 (KRaft), React 19 · TypeScript · Vite 7, JUnit 5 · Mockito · Testcontainers, k6, Prometheus · Grafana, Docker Compose, GitHub Actions

- **정산** — 배달완료 기준 일 정산, 관리자 확정 → 지급, 정산 감사 이력과 누락분 재집계

- **운영** — Flyway 마이그레이션, prod 프로필 필수 값 점검, TraceId 로깅, Prometheus · Grafana 대시보드와 알림 규칙

패키지는 `controller · service · entity · repository` 계층에 `event`(Outbox · Kafka), `lock`, `scheduler`(정산), `maintenance`(보관 기간 정리), `logging` 을 더해 구성했습니다. 토스페이먼츠 연동은 `pg`, 소셜 로그인은 `social`, 메일 발송은 `mail` 패키지로 분리했습니다.

요청과 이벤트는 다음 순서로 흐릅니다.

1. Spring Security 의 JWT 필터가 토큰과 URL 별 역할을 검사하고, Service 는 소유권 · 역할을 DB 기준으로 한 번 더 확인합니다.
2. 상태 전이와 수수료 계산은 Entity 에 두어 규칙이 한곳에 모이게 했습니다.
3. 결제 · 환불 · 배달완료 같은 업무 변경은 같은 트랜잭션에 Outbox 이벤트로 저장되고, 별도 Publisher 가 Kafka 로 발행합니다. 알림 Consumer 가 알림을 저장한 뒤 커밋 후 SSE 로 사장님 화면에 전달합니다.
4. 정산 스케줄러는 매일 01:10 에 전날 배달완료 건을 집계하며, 여러 인스턴스 중 한 대만 실행되도록 Redis 분산 락을 씁니다.

## 핵심 구현 및 설계 결정

### 1. 결제 중복 방지와 멱등성

**배경** — 클라이언트 재시도로 같은 결제 요청이 두 번 오거나, 여러 인스턴스의 정산 스케줄러가 동시에 실행될 수 있었습니다.

**설계 · 구현**

- DB UNIQUE 제약(주문당 결제 1건, 매장 · 날짜당 정산 1건)을 최종 방어선으로 두고 Redis 를 보조 수단으로 활용했습니다.
- `Idempotency-Key` 로 첫 응답을 재전송합니다. 같은 키에 다른 요청은 422, Redis 장애 시 키가 있는 새 결제는 503 으로 막아 데이터를 바꾸는 쪽으로 진행하지 않습니다.
- 멱등 기록을 결제와 **같은 트랜잭션**에 DB 로도 저장해 Redis 기록이 사라져도 재전송할 수 있게 했습니다.
- 정산 스케줄러는 Redis 분산 락으로 한 대만 실행하고, Redis 장애 시에는 건너뛴 뒤 다음 실행에서 보충합니다.

**검증** — Testcontainers Redis 로 재전송 · 동시 요청 · Redis 장애를 재현했습니다(`PaymentIdempotencyIntegrationTest`, `PaymentIdempotencyRedisFailureTest`, `SettlementSchedulerLockTest`). 같은 키 동시 결제 부하 결과는 아래 [성능 개선 및 검증](#성능-개선-및-검증)에 정리했습니다.

### 2. 외부 결제 시스템 장애 대응

**배경** — 토스페이먼츠 승인 · 취소가 시간 초과되면 실제로 처리됐는지 알 수 없습니다. 실패로 보고 결제창을 다시 열면 이중 결제, 취소를 다시 보내면 부분 취소의 경우 이중 환불이 됩니다. 외부 응답을 기다리며 주문 행 잠금을 쥐면 수락 · 취소도 막힙니다.

**설계 · 구현**

- 금액 · 주문번호 · 주문 상태를 승인 **전에** 대조하고, 맞지 않으면 토스 승인을 호출하지 않습니다.
- 승인 호출은 트랜잭션 밖에서 하고, 앞뒤 확인 · 기록만 짧은 트랜잭션으로 처리합니다. 기다리는 사이 주문이 바뀌어 기록할 수 없으면 보상 취소합니다.
- 타임아웃이 발생해도 실패로 단정하지 않고 조회 API 로 실제 처리 결과를 확인하도록 했습니다. 결과를 확인할 수 없으면 503 `PG_RESULT_UNKNOWN` 을 돌려주고, 화면은 결제창 대신 **같은 요청만** 재시도합니다. 승인은 토스 멱등 키와 결제 키 UNIQUE 로 1회만 반영됩니다.
- 취소 · 환불은 DB 확정 후 요청을 기록하고(Outbox 와 같은 방식) 커밋 후 호출 · 백오프 재시도합니다. 부분 취소는 재시도 전 잔액을 확인해 중복 환불을 막았고, 같은 결제의 취소는 순서대로 하나씩 처리합니다.

**검증** — 가짜 PG 모드와 Mockito 로 응답 유실 · PG 지연 · 승인 중 주문 취소 · 취소 시간 초과를 재현했습니다(`TossPaymentIntegrationTest`, `FakeTossPaymentIntegrationTest`).

### 3. 정산 정합성: 확정된 기록을 고치지 않는 정산

**배경** — 배달완료 후 환불이 생기면 이미 만들어진(또는 지급된) 정산과 어긋납니다. 기존 정산을 수정하면 지급 기록과 감사 근거가 사라집니다.

**설계 · 구현**

- 정산 기준 시점은 배달완료 시각(일 정산, Asia/Seoul)으로 정했습니다.
- 확정된 정산 기록은 수정하지 않고 상태 전이(대기 → 확정 → 지급)만 허용합니다. 환불 금액은 이후 정산에서 차감하고, 부족한 금액은 다음 정산으로 이월하도록 설계했습니다.
- 수수료는 결제 시점에 원 단위로 한 번만 반올림하고 정산액 = 결제액 − 수수료 로 계산해 1원 오차가 생기지 않게 했습니다.
- 중복 차감은 매장 행 잠금과 환불 · 이월 기록의 UNIQUE 제약으로 이중 방어합니다.
- 확정 · 지급 처리자와 시각은 감사 이력으로 남기고, 집계 실패는 DB 에 기록해 관리자가 누락 · 실패분만 재집계합니다(기존 정산은 재계산하지 않음).

**검증** — 지급액 = 판매 정산액 − 환불 정산액 + 미차감 이월분 이라는 회계 항등식을 `PaymentRefundIntegrationTest` 로 고정했고, 날짜 역순 · 동시 집계에서도 총 지급액이 같음을 확인했습니다.

### 4. 이벤트 유실과 중복 처리 방지

**배경** — 업무 트랜잭션 안에서 Kafka 로 바로 보내면 롤백된 결제의 이벤트가 나가거나, 커밋 후 전송 실패로 이벤트가 유실됩니다. Kafka 가 느리면 결제도 느려집니다.

**설계 · 구현**

- 업무 트랜잭션에서 Outbox 이벤트를 함께 저장하고 별도 Publisher 가 Kafka 로 발행하도록 구성했습니다. 트랜잭션 밖에서 Outbox 저장을 호출하면 실패하도록(`Propagation.MANDATORY`) 막았습니다.
- `FOR UPDATE ... SKIP LOCKED` 로 여러 인스턴스의 중복 발행을 막고, 메시지 키를 주문 id 로 두어 주문 단위 순서를 보장합니다. 실패는 지수 백오프로 재시도하고 한도를 넘으면 FAILED 로 남겨 관리자가 재발행합니다.
- 발행은 최소 한 번이므로 Consumer 는 `eventId` 기준으로 멱등하게 처리합니다. 처리 실패는 재시도 후 DLT 로 보내고, 원인을 해결한 뒤 되돌리는 재처리 CLI 를 구현했습니다.
- Kafka 가 멈춰도 결제는 성공하고 이벤트는 회복 후 발행됩니다.

**검증** — 실제 Kafka 컨테이너로 원자성 · 중복 수신 · DLT · 재처리를 테스트했습니다. 로컬 수동 검증(2026-11-15)에서는 DB 장애 → DLT 적재까지 126.6초, 재처리 후 약 70ms 뒤 알림 저장을 확인했습니다.

### 5. 사장님 실시간 주문 알림 (SSE)

**설계 · 구현**

- 결제 완료 · 고객 취소를 접속 중인 사장님 화면에 SSE 로 전달합니다. 알림 저장이 **커밋된 뒤** 전용 스레드에서 보내 Kafka 소비 스레드를 막지 않고, 이벤트는 "목록을 다시 받으라"는 신호로만 씁니다.
- 토큰을 URL 에 넣지 않도록 `EventSource` 대신 fetch 스트림을 썼습니다. 연결은 Access Token 만료보다 짧은 10분 뒤 끊어, 재연결할 때 권한을 다시 확인합니다.
- 화면은 끊기면 백오프로 재연결하고, 연속 3번 실패하면 30초 주기 조회로 대체합니다.

**검증** — 로컬 compose(2026-11-21, Kafka 경유)에서 결제 후 약 2.3초 만에 사장님 화면이 이벤트를 받았습니다. 연결 중 DB 커넥션 문제는 아래 트러블슈팅에 정리했습니다.

## 성능 개선 및 검증

### 대용량 주문 조회 (#40 · #54)

**문제** — 주문 목록 API 가 전체 행을 한 번에 반환하고 주문 항목을 건마다 조회(N+1)했습니다. 사장님 한 명이 주문 7,500건을 가진 데이터에서 요청 한 번에 쿼리가 7,507번 실행됐습니다.

**개선**

- 전체 조회를 페이징으로 전환하고(`Slice`, count 쿼리 없음), 주문 항목은 `IN` 일괄 조회로 바꿔 요청당 쿼리를 3번으로 고정해 N+1 문제를 제거했습니다.
- 인덱스는 EXPLAIN 근거가 있는 것만 추가했습니다.
- 이후 OFFSET 방식의 마지막 페이지 병목을 EXPLAIN 으로 확인하고, 이 경로에만 Keyset Pagination(`?afterId=`)을 적용했습니다. 기존 `?page=` 는 그대로 두어 호환성을 유지했습니다.

**측정 조건** (`docs/performance.md` 3 · 9장)

- 도구: k6 v1.3.0 (호스트에서 직접 실행), 동시 사용자 20명이 대기 없이 반복 요청, API 마다 워밍업 10초 후 30초 · 1회 측정
- 데이터: 합성 데이터 주문 30만 건 · 주문 항목 60만 건 (고객 1,000 · 매장 200, 사장님 1명당 주문 7,500건)
- 환경: 노트북 1대(Ryzen 5 7430U, RAM 16GB, Windows 11)에 앱(JDK 21, `-Xmx1g`, HikariCP 10) · PostgreSQL 18(Docker) · k6 를 함께 실행
- 시기: #40(2026-11-14 병합) · #54(2026-11-15 병합) 작업 중 측정

**결과**

| 요청 | 개선 전 | 개선 후 |
| --- | --- | --- |
| 사장님 주문 목록 (전체 → 첫 페이지) | 평균 15,982ms · 1.1 req/s | 평균 **19.0ms** · 1,028 req/s |
| 고객 주문 목록 (전체 → 첫 페이지) | 평균 1,205ms · 16 req/s | 평균 18.0ms · 1,082 req/s |
| 사장님 마지막 페이지 (OFFSET → Keyset) | 평균 426ms · 47 req/s | 평균 **17.6ms** · 1,111 req/s |

**해석**

- 첫 페이지 비교는 "전체 조회 → 20건 페이지"이므로 개선 폭의 대부분은 페이징과 N+1 제거 효과입니다.
- OFFSET 은 뒤쪽 페이지일수록 앞의 행을 모두 읽고 버려 사장님 주문 수에 비례해 느려졌습니다. Keyset 은 첫 · 중간 · 마지막 페이지 응답 시간이 거의 같았습니다.

**한계**

- Keyset 은 임의 페이지로 바로 이동할 수 없고, 다른 정렬을 추가하면 `(정렬 컬럼, id)` 복합 조건과 인덱스가 필요합니다.
- 위 수치는 id 오름차순 정렬일 때 측정한 값입니다. 이후 주문 목록을 최신순으로 바꾼 변경(#98)은 아직 다시 측정하지 않았습니다.
- 같은 OFFSET 마지막 페이지도 실행마다 차이가 있어(426ms · 538ms), 같은 실행 안의 전후 비교로만 해석했습니다.

### 주문 · 결제 쓰기 경로와 같은 키 동시 결제 (#68)

**측정 조건** (2026-11-20, `docs/performance.md` 11장) — 고객 로그인 → 주문 생성 → 결제(`Idempotency-Key`)를 동시 사용자 10 · 20 · 50명으로 워밍업 10초 후 60초씩 1회 측정했습니다. k6 v1.3.0 을 compose 네트워크 안에서 실행했고, 같은 노트북의 Docker Desktop 에 앱 · PostgreSQL · Redis · Kafka · Prometheus · Grafana 를 함께 올렸습니다.

**결과**

- 처리량은 10명 184.0 → 20명 284.7 → 50명 303.7 흐름/s, 모든 단계 오류율 0% 였습니다.
- 주문 20건마다 동시 요청 50건을 같은 키 · 같은 본문으로 보낸 결과(총 1,000건), 주문마다 새 결제는 정확히 1건이었고 결제가 2건 이상인 주문은 0건이었습니다.

**해석 · 한계**

- 20 → 50명에서 처리량은 7% 늘고 p95 는 2.5배가 됐습니다. 커넥션 풀을 20으로 늘려도 처리량이 같아(303.7 → 314.3) 상한은 풀이 아니라 한 노트북에서 앱 · DB · Kafka · k6 가 CPU 를 나눠 쓰는 환경이라고 판단했습니다.
- Outbox 발행 속도(약 92건/s)가 결제 속도보다 느려 부하 중 발행 대기가 쌓였습니다. 결제 응답에는 영향이 없지만 알림이 늦어지므로 발행 처리량 개선을 후속 과제로 분리했습니다.
- 단계별 1회 · 60초 측정이라 실행 편차와 장시간 부하는 확인하지 않았습니다.

※ 성능 수치는 로컬 단일 머신의 합성 데이터 및 부하 테스트 기준이며, 실제 운영 환경의 성능을 보장하는 수치는 아닙니다.

- **테스트**: 백엔드 테스트 1,001건(114개 클래스), 프론트엔드 테스트 116건 — 2026-11-24 전체 실행 기준
- **통합 테스트**: Testcontainers 기반 PostgreSQL · Redis · Kafka 통합 테스트. 동시 결제 · 동시 집계 · 마이그레이션(기존 데이터가 있는 DB 에 새 버전 적용)까지 실제 DB 로 확인했습니다.
- **성능 분석**: k6 부하 테스트 및 EXPLAIN ANALYZE 기반 성능 분석, 측정 스크립트는 저장소 `perf/` 에 남겼습니다.
- **CI**: GitHub Actions CI 구성 — main 대상 PR · push 에서 백엔드 `./gradlew build`, 프론트엔드가 바뀌면 `npm test` · 빌드를 실행합니다.
- **모니터링**: 로컬 compose 에 Prometheus · Grafana 대시보드(HTTP · DB, Outbox · Kafka, 알림, Redis, 정산 스케줄러)와 알림 규칙을 두었습니다.
- **배포**: Render · Vercel 기반 공개 데모 배포. 비용 없이 시연하기 위해 프론트엔드는 Vercel, 백엔드는 Render Free, DB 는 Neon(PostgreSQL), Redis 는 Upstash 무료 플랜을 썼습니다. Vercel 이 `/api` 요청을 백엔드로 프록시해 Refresh Token 쿠키가 같은 출처로 동작합니다.
  - 무료 플랜에 상시 Kafka 가 없어 데모 백엔드는 Kafka 를 빼고 Outbox 이벤트를 같은 프로세스에서 직접 전달하는 프로필로 실행합니다. Outbox 저장 · 재시도 · 중복 제거는 그대로이고, Kafka · DLT 경로는 로컬 compose 와 테스트로 검증했습니다.
  - 유휴 시 서버가 절전되므로 화면이 먼저 서버를 깨우고 안내 배너를 띄웁니다. 기동 시 데모 데이터를 만들고, 고객 · 사장님 · 관리자 체험 로그인을 제공합니다.
